## 三、三种方案对比

### 方案 A：ArkTS 原生重写客户端 + 复用现有云端后端 ⭐ 推荐

```
┌─────────────────────────┐
│  HarmonyOS App (ArkTS)  │
│  ArkUI 页面 + Map Kit   │
└───────────┬─────────────┘
            │ HTTP (JSON)
┌───────────▼─────────────┐
│ Cloudflare Pages Func.  │  ← 现有，零改动
│ D1 数据库 + R2 图片     │
│ 高德核验 + 智谱 AI      │
└─────────────────────────┘
```

- **优点**：完全符合"基于 DevEco Studio 开发应用"的要求；技术栈正宗；后端现成，工作量集中在客户端（也是老师重点看的部分）；演示时数据是真实的
- **缺点**：ArkTS/ArkUI 需要学习成本（若有前端基础，1-2 天能上手）
- **工作量**：约 7-10 天（业余）/ 4-5 天（集中开发）

### 方案 B：WebView 套壳现有网页

- **优点**：1-2 天就能出成果，几乎零风险
- **缺点**：**风险很高**——老师很可能判定"这不是原生应用"，分数打折；无法体现 ArkTS 能力；答辩被追问时不好解释
- **结论**：不推荐，仅作为时间极度紧张时的保底

### 方案 C：原生 UI + 地图用 WebView（混合）

- 除地图外的页面用 ArkUI 原生，地图页用 WebView 加载高德 H5
- **优点**：绕开 Map Kit 的账号配置麻烦，同时主体仍是原生应用
- **缺点**：地图交互体验不如原生；WebView 与原生通信要写桥接
- **结论**：作为**方案 A 遇到 Map Kit 卡住时的降级路径**，提前准备好

### 4.3 网络层封装（可直接用的骨架）

```ts
// common/utils/HttpUtil.ets
import http from '@ohos.net.http';
import { Preferences } from '../constants/Api';

const BASE_URL = 'https://qymap.pages.dev/api';

function buildUrl(path: string, params?: Record<string, string>): string {
  let url = `${BASE_URL}${path}`;
  if (params && Object.keys(params).length > 0) {
    url += '?' + Object.entries(params)
      .map(([k, v]) => `${k}=${encodeURIComponent(v)}`)
      .join('&');
  }
  return url;
}

async function request<T>(path: string, method: http.RequestMethod,
  params?: Record<string, string>, body?: object, token?: string): Promise<T> {
  const httpRequest = http.createHttp();
  const header: Record<string, string> = { 'Content-Type': 'application/json' };
  if (token) header['Authorization'] = `Bearer ${token}`;

  const response = await httpRequest.request(buildUrl(path, params), {
    method: method,
    header: header,
    extraData: body ? JSON.stringify(body) : undefined,
    expectDataType: http.HttpDataType.STRING,
    connectTimeout: 10000,
    readTimeout: 10000
  });
  httpRequest.destroy();

  if (response.responseCode < 200 || response.responseCode >= 300) {
    throw new Error(`请求失败：HTTP ${response.responseCode}`);
  }
  return JSON.parse(response.result as string) as T;
}

export const api = {
  // 点位列表（后端真分页）
  listSpots: (page: number, pageSize: number, category?: string, keyword?: string) =>
    request<SpotListResponse>('/spots', http.RequestMethod.GET,
      { page: String(page), limit: String(pageSize),
        ...(category && category !== 'all' ? { category } : {}),
        ...(keyword ? { q: keyword } : {}) }),

  // 地图图钉（轻量字段，一次拿全量坐标）
  mapSpots: () => request<SpotListResponse>('/spots', http.RequestMethod.GET,
    { fields: 'map', limit: '500' }),

  // AI 推荐
  recommend: (prompt: string, center: { lat: number; lng: number }) =>
    request<RecommendResponse>('/recommend', http.RequestMethod.POST,
      undefined, { prompt, center }),

  login: (username: string, password: string) =>
    request<AuthResponse>('/auth/login', http.RequestMethod.POST,
      undefined, { username, password })
};
```

### 4.5 地图实现（两种路线，建议先试 Map Kit）

**路线 1：Map Kit（原生，推荐）**
- 在 AppGallery Connect 开通"地图服务"，获取 `client_id`
- `module.json5` 配置 `metadata` → `client_id`
- 使用 `MapComponent` + `mapController.addMarker()` 打点
- 需要配置签名证书指纹（这是最容易卡住的环节，预留半天）

**路线 2：WebView 加载高德 H5（降级方案）**
- 复用现有 `index.html` 的地图部分，或写一个只含地图的 H5 页
- 通过 `javaScriptProxy` 做原生 ↔ H5 通信（点击图钉回调原生）
- 优点：不依赖华为账号配置；缺点：体验略逊

建议两条线并行准备：**Map Kit 配不通就用 WebView**，不阻塞整体进度。

```
│  网页版       │  │  HarmonyOS App  │  │  管理后台     │
│ index.html   │  │  ArkTS 客户端    │  │ admin.html   │
└──────┬───────┘  └────────┬────────┘  └──────┬───────┘

              ┌────────────▼────────────┐
              │ Cloudflare Pages Func.  │
              │ D1（同一数据库）         │

```

三端共用同一个数据库、同一套密钥、同一份图片，天然数据互通。

#### 共享范围明细

| 能力 | 是否共享 | 说明 |
| --- | --- | --- |
| 点位数据 | ✅ | 网页提交的点位 App 立即可见；App 提交的由网页后台审核 |
| 用户账号 | ✅ | 同一 `users` 表，网页注册的账号 App 可直接登录 |
| 图片资源 | ✅ | 统一存 R2，通过 `/api/images/:key` 访问 |
| AI 推荐 | ✅ | 共用智谱密钥与 `/api/recommend`，App 无需另外申请 |
| 高德自动核验 | ✅ | 核验逻辑在后端，App 直接受益 |
| 管理后台 | ✅ | 继续用现有网页后台审核 App 提交的点位、处理举报 |
| 点赞身份 | ⚠️ 不互通 | `X-Actor-Token` 由客户端本地生成，两端各自独立（同一账号两端各可点赞一次） |

#### 为什么原生 App 能直接调（不受跨域限制）

浏览器的同源策略（CORS）只约束网页，原生 App 发出的 HTTP 请求**不受 CORS 约束**。后端现有的跨域配置对鸿蒙端不构成任何障碍，`https://qymap.pages.dev/api` 直接可调。

#### 需要注意的三点

| 项目 | 说明 | 应对 |
| --- | --- | --- |
| **国内访问稳定性** | `*.pages.dev` 在国内偶有波动，电脑能访问不代表真机（校园网 / 手机流量）能访问 | **第一步就在鸿蒙设备里发一次请求验证**；不稳则绑定自定义域名或走离线兜底 |
| **免费额度** | D1 5GB、Pages Functions 每日十万级请求；期末演示量级远低于上限 | 无需处理 |
| **点赞身份跨端** | 两端各生成独立 token | 影响极小；若要统一，可改为与登录账号绑定（后端小改） |

#### 必做的兜底：内置离线数据

演示现场断网 = App 变空白，这是最大事故。建议：

1. 导出当前 13 条点位为 `spots.json`，放进 App 的 `resources/rawfile/`
2. 启动时先加载兜底数据渲染，再发起网络请求刷新
3. 网络成功 → 覆盖兜底数据并写入 RelationalStore 缓存
4. 网络失败 → 保持兜底数据 + 顶部提示"离线模式"

这样即使全程无网，地图和列表也有内容可演示。

#### 多端同步能力（2026-10-10 后端已实现）

以下能力已上线，App 直接按约定调用即可。

| 能力 | 接口约定 | 说明 |
| --- | --- | --- |
| **点赞跨端同步** | `POST /api/spots/:id/like` 带 `Authorization: Bearer <token>` | 登录状态下点赞记在账号下（`actor_key = user:<id>`），网页与 App 状态一致；未登录时仍用本地随机串 |
| **点赞状态回传** | `GET /api/spots?page=&limit=` 带 `Authorization` | 每条数据附带 `liked: true/false`，App 据此渲染实心/空心赞 |
| **增量同步** | `GET /api/spots?since=2026-10-10 12:00:00` | 只返回该时间点之后新增或变更的点位，配合轮询极省流量 |
| **离线提交幂等** | `POST /api/spots` 请求体带 `client_token: <UUID>` | 客户端离线队列重发时，同一 `client_token` 只写入一次；重复提交返回 `200` + `duplicated: true` |

实现要点（后端已落地，App 端照此对接）：

1. **轮询同步**：App 记录上次同步时间 `lastSync`，每次拉 `/api/spots?since=${lastSync}`，成功后更新 `lastSync`。建议 30 秒一次 + 下拉手动触发。
2. **离线队列**：提交失败（无网 / 超时）时把请求体连同 `client_token` 写入本地数据库；联网后依次重发，收到 `duplicated: true` 视为成功并出队。
3. **点赞渲染**：列表接口返回的 `liked` 为权威值，本地只做乐观更新，以服务端结果为准。

数据库迁移已执行：`migration-sync.sql`（新增 `updated_at` 用于增量判断，`client_token` 唯一索引用于幂等）。

#### 后端是否需要改动

**基本不需要**。可选的增强（按需）：

| 增强项 | 价值 | 优先级 |
| --- | --- | --- |
| `GET /api/spots/:id` 单条详情 | 详情场景更省流量 | 低（列表接口已返回全部字段） |
| 离线同步接口（按 `updated_at` 增量拉取） | 配合离线缓存更规范 | 低 |
| 点赞身份与账号绑定 | 跨端一致 | 低 |
| 为 App 单独加统计埋点 | 演示时展示访问量 | 低 |

## 六、风险与应对

| 风险 | 影响 | 应对措施 |
| --- | --- | --- |
| **Map Kit 配置卡住**（client_id / 签名指纹 / AGC 开通） | 地图页做不出来 | 提前 1 天单独攻克；不通就切 WebView 方案 |
| **答辩现场无网 / 网络差** | 所有数据加载失败 | 用 RelationalStore 做离线缓存 + 预置 13 条点位兜底；演示前确认网络 |
| **AI 推荐限流**（免费模型高峰期 1305） | 推荐页偶尔失败 | 页面做好失败提示；可预先缓存一条示例结果 |
| **高德自动核验偶发失败** | 提交后转人工审核 | 属正常行为，答辩时讲清"双保险机制"反而加分 |
| **ArkTS 语法与 TS 差异**（严格类型、无 any 滥用、装饰器） | 编译报错反复 | 先用官方模板起步，逐步替换；善用 DevEco 的自动修复 |
| **模拟器性能 / 真机调试** | 调试慢 | 优先用本地模拟器；Map Kit 建议真机验证 |
| **老师质疑"后端不是自己写的"** | 分数争议 | 答辩时讲清"前后端分离架构"，客户端是你完整实现的；后端也是我们这学期做的同一项目 |
| **时间不够** | 做不完 | 按第八节裁剪 MVP |
